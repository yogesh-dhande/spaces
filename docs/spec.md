# Spaces Spec

This document defines how Spaces should behave from the user's point of view. It is the source of truth for UX and product semantics. Implementation choices and the rationale behind them belong in [implementation.md](implementation.md).

## Product Intent
Spaces is a local macOS control plane for switching between coding contexts quickly.

It should reduce the overhead of:
- creating and cleaning up workspaces and worktrees
- starting the right processes with the right service ports and environment
- reopening the right browser and terminal windows
- switching focus to the right window set
- noticing attention items such as failed processes or coding agents waiting on a human

Spaces provides a desktop app and a CLI for power users and coding agents.

The public website links to the Spaces GitHub repository from the header and footer,
and its download actions point to the latest GitHub Release. Its localhost comparison
limits cross-port sharing to cookie-based sessions, while the routed hostname comparison
explains that separate hostnames isolate cookies and local storage. Hero specification
values wrap on narrow screens instead of overlapping adjacent values.

## Non-Goals
- Spaces does not manage window geometry or tiling. It simply focuses windows as laid out by the user.
- Spaces does not restore exact browser tab ordering.
- Spaces does not inspect editor internals.
- Spaces does not manage secrets beyond environment variables needed for the app to function.
- Spaces only supports the browser and terminal integrations it explicitly implements.

## Key Design Decisions
- Separate window per process.
  Dedicated process windows keep each terminal focus target stable because Spaces cannot predict which terminals a user will want side by side later.
- Browser sessions are lazy bookmarks that open in Chrome only when focused.
  Some workspaces may carry many useful URLs, but opening all of them during launch or restart is wasteful when the user may only need a subset in a given session. Focused sessions for the same workspace share an existing workspace Chrome window as tabs when one is available.
- Focus a browser session by URL.
  Spaces uses the tracked Chrome window when available, scans Chrome windows to adopt a matching tab that the user moved by hand, and opens the URL as a tab in an existing workspace Chrome window when the session is not already open.
- Closing a terminal pane detaches the client from the session it hosted.
  Closing a process or coding-agent pane leaves the runtime running and recoverable through focus. Closing an ad hoc terminal's pane stops that ad hoc session. Explicit Stop and Restart controls own process and coding-agent runtime termination.
- Keep workspace lifecycle separate from runtime health.
  `Running` and `Stopped` should stay easy to explain, while failed processes or stale tracked windows surface as warnings on top of that lifecycle state.
- Require explicit named targets for GUI-driven and harness-driven focus.
  Focus should not guess which window the user meant, because arbitrary focus becomes unpredictable as workspaces collect multiple windows.
  Example: one workspace may have a frontend browser, an admin browser, an API terminal, and a coding-agent terminal all open at once. If the user clicks Focus in the GUI or a test harness focuses a named target, Spaces should not silently pick whichever target was captured first or happened to survive most recently. The user may want the admin browser now and the coding-agent terminal five seconds later. Requiring an explicit target name keeps focus behavior deterministic.
- Never resize or reposition tracked windows unless initiated by the user.
  Spaces should respect where the user placed each tracked window, because it cannot infer whether the user wants side-by-side windows, overlapping windows, or some other layout that includes non-Spaces windows.
- Never control windows that Spaces does not explicitly track.
  Spaces should not hide, move, resize, close, or otherwise manipulate unrelated windows, because the user may intentionally keep an untracked window visible next to a tracked workspace window. Direct browser-session focus may adopt a Chrome tab whose URL matches the focused workspace session, so user-moved session tabs keep working.
- Keep coding-agent events explicit.
  Workspace creation, start, and restart actions must not infer agent lifecycle, because only the agent can accurately report when it actually initialized, started active work, is blocked, is done, or exited.
- Use explicit names as the stable identity surface for focusable browser sessions, processes, and coding-agent terminals.
  Names express purpose and intent, stay meaningful when URLs or process commands change, and avoid collisions where multiple coding agents may run the same command. Those names must be unique within a workspace's combined focusable set so GUI and harness focus can target one unambiguous window by name.

## Core Concepts

### Project
A project is a codebase plus reusable templates:
- setup and stop scripts
- service definitions
- process templates
- browser sessions

Users configure a project once, then derive workspaces from it.

### Workspace
A workspace is an isolated stream of work for one project.

A workspace has:
- a directory
- a title
- optional notes text
- an optional git branch
- per-workspace overrides for launch-time settings
- a captured set of windows and runtime state

Workspaces can be visible or hidden in the sidebar, and can be running or stopped independently of that sidebar state.
Hidden workspaces live in a collapsed `Hidden` section in the sidebar.
Running and stopped should be easy to explain:
- `Running` means Spaces explicitly launched the workspace or another explicit workspace action marked it running.
- `Stopped` means the workspace is idle. This covers two cases that behave the same: a workspace Spaces has never launched, and one Spaces explicitly stopped after a run. In both, nothing is running and the workspace is directly launchable.
- Stale runtime leftovers should not silently change `Stopped` back to `Running`; they should surface as warnings on top of the existing lifecycle state.

### Window Set
A workspace owns a tracked set of focus targets, such as:
- process terminals
- browser-session tabs in Chrome windows that have been opened or adopted on demand
- coding-agent terminal windows

Spaces focuses those targets; it does not decide window geometry.

### Terminal sessions
Every terminal runs in the built-in terminal, never an external terminal app. A workspace can hold three kinds:
- a process terminal hosting a configured process
- a coding-agent terminal hosting a configured or detected coding agent
- an ad hoc terminal the user opens directly (for example through `New terminal`), rooted at the workspace directory

#### Session names
- Every terminal has a name that identifies it and keeps still: a process or coding-agent terminal takes its name from its configured row, and an ad hoc terminal from a generic shell name (`shell-1`) until the user renames it. What the program inside prints never becomes the name.
- An ad hoc terminal row also shows the title its program reports (for example `vim main.swift`) as dimmed secondary text beside its name, so one glance reads both which terminal it is and what it is doing. A terminal whose program has reported no title shows its name alone. Process and coding-agent rows show what they run instead, as they always have. This pairing is what the sidebar, the command palette, the session picker, the iOS session list, and a bell's row under Alerts all show.
- Renaming an ad hoc terminal changes its name and nothing else; its program's title keeps showing beside the new name. Renaming it to an empty name restores the generic name it was launched under. Configured rows rename their settings entry instead, which must keep a name, so an empty rename there is discarded.
- A terminal tab is named after its selected pane, and a panel window after its selected tab, so splitting a tab and moving focus renames the tab and the window with it. Tabs carry the name, never the live title — the sidebar is where the live title is read.
- The command palette matches a target's name first and its secondary text second, so typing a name outranks typing what a program printed.

## Startup
- On launch, the main window should immediately show a neutral loading state while Spaces loads workspace data, so startup never presents a blank window.
- Launch runs a setup flow before the main workspace UI, showing only the steps that are pending. A launch with nothing pending goes straight to the workspace UI and the flow is never seen. The steps are the Chrome Automation permission, then coding-agent hooks.
- Spaces focuses workspace browser sessions by scripting Google Chrome through Apple Events, which macOS gates under the Automation privacy permission ("Spaces wants to control Google Chrome"). This Automation permission is the only blocking prerequisite; there is no Accessibility requirement.
- When that permission is missing — not yet granted, or previously denied — launch shows a blocking "Allow Spaces to control Google Chrome" setup screen before the main workspace UI. The screen offers:
  - a single primary action whose label follows the state: "Grant Access" raises the macOS consent prompt while the permission is still undecided, and "Open System Settings" deep-links to System Settings ▸ Privacy & Security ▸ Automation after a denial (macOS does not re-prompt after a denial), alongside a Recheck action.
  - a suppressed-prompt state for the case where macOS declines to show the consent prompt at all because a permission record from a previous Spaces build is in the way. The screen explains how to reset that stale record (a `tccutil reset AppleEvents` for the app's bundle id) and to click Recheck afterward.
  - The screen polls the permission and auto-advances to the workspace UI the moment access is granted, so granting through System Settings does not require relaunching Spaces.
- When Google Chrome is not installed, or the permission state cannot be determined, Spaces does not block and opens straight to the main UI, because there is nothing to grant. The macOS Automation prompt then appears the first time a browser session is focused.
- Installed builds should default to one shared profile rooted at `~/.spaces/`, while repo-local development builds should default to one profile per git worktree. (Profile and environment-override mechanics live in [implementation.md](implementation.md).)
- Every Spaces terminal session should carry the profile of the Spaces instance that launched it. A `spaces` command run inside a session — typed by hand, or invoked by a coding agent's hook — should act on that session's profile whichever `spaces` build the command resolves to, so one machine-wide agent hook configuration stays correct for the installed app and every development profile at the same time.
- App launch should not stall on the user's shell startup files while resolving command locations.
- Spaces should treat its built-in terminal as the only supported terminal path and should not require any external terminal app. Installed terminals provide the `xterm-ghostty` terminfo entry so terminal-aware and curses applications recognize the terminal.
- A standard Spaces app installation includes everything required to create and render built-in terminals; it does not require a repository checkout or terminal-specific environment variables.
- Workspace processes launch, stop, recover, and reopen through Spaces-owned built-in terminal sessions.
- Launching a second app instance for the same profile should fail immediately and identify the existing owner process.
- Launching a different profile while another Spaces instance already owns desktop-global control should still load profile data and windows, but it should start in passive mode with local in-app shortcuts only and a status that global shortcuts are unavailable.

## Projects
- Users can add a project from a directory path or a git URL.
- The New Project form opens in its own dialog window with the same header as the Settings window, dismissed with the close button, Cancel, or `Esc`.
- Adding a project is a step-by-step flow, each step in the same dialog: **Device** (skipped when the local Mac is the only device) → **Source** → **Configure**. Each choice is fixed once made; there is no Back, and canceling requires re-entering the flow. Steps are presented as lists of clickable rows where a choice is being made.
- The **Device** step lists each paired device as a row; clicking one advances to the source step. An offline device is shown disabled and cannot be selected, since creating a project on an unreachable daemon would only stall. The local device's row is labeled "Local" with a "This device" caption; each remote device's row shows its stored name with a "Remote device" caption.
- The **Source** step offers two clickable rows — **Existing folder** and **Clone a repo** — the selected one reveals its input (a folder path with directory autocomplete, or a Git repository URL). **Continue** validates the input and loads the configuration for the next step: for a folder the chosen device validates the path and reads any `spaces.yaml`; for a repo it reads `spaces.yaml` directly from the declared default branch, fetching only that one file without cloning. A load failure (invalid path, unreachable repo, undeterminable default branch, or invalid YAML) surfaces the error and keeps the user on the source step. Because source selection is its own step, there is no source toggle to switch after configuration has loaded.
- The folder path input is a text field with directory autocomplete, not a native file picker, so projects can be created by path on the local Mac or on the chosen remote device; suggestions come from the chosen device's filesystem.
- Git imports should create an app-managed clone and default workspace.
- Non-git projects should create one default workspace for the project directory.
- Project creation and deletion should show progress without freezing the UI.
- Git project rows expand or collapse their workspace lists either by clicking the row's name area or with a dedicated expand/collapse control.
- Sidebar project row collapsed state should persist across app restarts and sidebar refreshes.
- Sidebar project rows should expose a dedicated settings action that opens project settings in a dialog. Opening the dialog leaves the current sidebar selection and detail pane unchanged.
- The project settings dialog matches the New Project dialog: a header with the project name and a close control, the directory path, then project-level configuration sections and footer actions. Closing the dialog discards unsaved edits; Save persists them.
- Project settings should support GUI-only `spaces.yaml` import and export. For local projects, `spaces.yaml` lives in the project directory. For app-managed Git imports, it lives in the checked-out default workspace directory, not the bare clone under the managed repos root.
- The **Configure** step shows the configuration sections populated from the source's `spaces.yaml` (empty when the source has none — for a repo with no `spaces.yaml`, a note says it was not found and to set up the configuration as needed). The user reviews and edits the sections, then Create.
- The repository is cloned only when the project is created: Create clones it, creates the default worktree from the declared default branch, and saves the project with the visible settings — the created project reflects those settings, not a re-read of the repository's `spaces.yaml` — so nothing is left behind if the user cancels.
- In the GUI, when a Git URL's managed clone or worktree folders already exist but are not registered to any project or workspace, the source step's Continue asks for confirmation that Create may replace them. Canceling stays on the source step; the folders are replaced only at Create.
- Export writes the saved project template as a full canonical `spaces.yaml`, overwriting the file at the project config path. Export requires project settings to have no pending unsaved edits, including open section editors and row drafts. Import loads a preview into the visible project settings without changing persisted project or workspace state, replacing open row drafts and editors with the imported rows.
- Saving project settings persists the visible project template. For a git project it does not rewrite any existing workspace settings, including the default workspace, unless Save confirms `Update All Workspaces` for a pending imported configuration; in that case Save applies the visible template to every workspace, including archived workspaces. `Project Only` saves only the project template, and `Cancel` leaves project and workspace state unchanged. The project settings dialog offers a discard action for pending imported configuration so the user can return to the previously saved project template before saving; discarding replaces open row drafts and editors with the saved rows.
- A non-git project owns exactly one workspace and can never create more, so its project template and that workspace's settings are one and the same: saving or importing project settings always syncs to that workspace so the edits are what actually run, and the `Update All Workspaces` / `Project Only` choice is never offered for a non-git project.
- Project configuration service rows trim and lowercase the entered service name, then commit valid names when the name field loses focus. Canceling a service edit discards the draft without committing it. Empty or invalid service names remain in edit mode and block project creation or project-settings save with a service-name message. Saved project-level service rows show `SPACES_<SERVICE>_PORT` and `SPACES_<SERVICE>_URL` hints next to the service name so those variables are visible while configuring processes.
- Expanding a project that has no workspaces shows a single `No workspaces yet` hint row so the expand/collapse control always reveals content; the hint is not selectable.
- Sidebar rows show their nesting. A project row distinguishes a git repository from a non-git directory, and a non-git directory conveys its run state. A git project's workspace rows nest one level under it and convey run state; their runtime-target rows nest a further level and carry their `⌘`-number shortcut hint. A non-git project's runtime-target rows nest one level under the project row, which stands in for the missing workspace level.
- Sidebar workspace rows show the git branch name. A non-git project owns a single workspace whose directory is the project directory, so it renders as one selectable row labeled with the project folder name, reading as a project rather than a nested workspace and conveying its run state. It can collapse its runtime targets, and clicking the row both selects it and toggles that collapse; it has no nested workspace row. Its settings action opens project settings like any project row, and because the project template stays in sync with this single workspace, those edits are what actually run — and project-level Delete and spaces.yaml import/export stay available from the same dialog.
- Sidebar workspaces under a project are ordered with the default workspace first, then the rest sorted alphabetically by display name (branch, or folder name for non-git) using natural, case-insensitive comparison, so the list is easy to scan.
- A workspace row can expand to show a list of its runtime targets, grouped by kind in a fixed order — browser sessions, configured processes (running or not), coding agents, then ad hoc terminals — which is the same order the numbered window shortcuts use, so a target's row position and its `⌘<number>` never disagree. The iOS Spaces tab lists a workspace's rows in this same order. Window cycling uses the already-open subset of those targets, ordered by the workspace's most recently focused targets at the start of the cycle burst. Targets convey their runtime state (running, exited, or not-started). When the workspace is selected, the selection covers the workspace row and its visible target rows; target rows show their `⌘<number>` shortcut hint, matching the command palette's ordering. A non-git project's row lists its single workspace's targets the same way, and its own control collapses them.
- Workspace rows are collapsed by default and only reveal their runtime-target list when expanded. A workspace with at least one runtime target can be expanded or collapsed; a workspace with no runtime targets offers no such control. Clicking a workspace row — or one of its target rows — pins it open, so it stays expanded even after the selection moves away, until the user collapses it. Leader-arrow navigation instead expands the selected workspace only transiently, as a preview: it collapses again as soon as the selection moves off it, unless it was pinned open by a click. Clicking the expand/collapse control toggles a workspace's expansion without changing the selection, and can collapse even the currently selected workspace. This expanded state lives in memory: it survives sidebar refreshes but not an app restart, where every workspace returns to collapsed.
- Left-clicking a sidebar target row selects the owning workspace and opens or focuses the target — the same behavior as its numbered shortcut or a command-palette row: terminal-backed targets open or focus their pane in the workspace's panel, browser sessions open or focus their Chrome tab, and not-yet-running configured processes and agent launchers start and open their terminal pane.
- The selected workspace's right panel is a tabbed terminal panel scoped to that workspace, and nothing else: a tab strip, the selected tab's panes, and the workspace footer strip. The main window shows no window title. The tab strip stays visible whether the window is windowed or fullscreen. The app identity row lives in the sidebar footer. The titlebar row keeps its native behaviors — dragging and double-click zoom work from its empty areas, including the tab strip's unoccupied space. Non-workspace detail panes such as Alerts do not show workspace tabs. Each tab holds one or more panes; every pane hosts a terminal session (future content kinds may join). A terminal session has at most one pane anywhere — opening an already-open session focuses its existing pane instead of duplicating it.
- Each tab conveys whether it is selected, and carries a close control. Clicking a tab selects it and returns keyboard focus to the pane that most recently held focus in that tab. Right-clicking a tab offers Rename, which edits the tab's name in place — the title becomes an inline field, like sidebar row renames (Return or clicking away saves, Esc cancels); a custom tab name persists with the layout and survives relaunch, and clearing it returns the tab to its derived title (its first pane's target). Tabs can be named independently of their panes' sessions, which matters once a tab holds several panes.
- Pane and derived tab titles use the runtime target's name (the same name the sidebar target row shows, e.g. `codex` or `npm:dev`), not the terminal's own window title. The tab strip holds the pane actions: split right, split down (both act on the selected tab's focused pane), and new tab. Splitting opens the command palette in a session-picker mode listing `New terminal session` first, then the workspace's sidebar runtime targets that are not already open in any pane (workspace panels or panel windows), in sidebar order — every loaded device's workspaces for a panel-window split. Browser sessions do not appear, since they cannot live in a pane. Picking a target behaves like its sidebar row: an exited target opens its pane in its ended state, and a not-started configured process or agent launcher starts and opens — except the pane lands at the picker's placement, the new split. The picker shows up to ten rows before any typing, and typing searches the full list; the picker appears even when `New terminal session` is the only row. Pane and tab sizes from divider drags persist.
- Clicking anywhere in a pane focuses it, and the next keystroke goes to that pane. A split tab marks its focused pane with an accent bar along the pane's top edge; a lone pane shows none, since there is nothing to disambiguate. The accent bar and the pane receiving keyboard input never disagree — one click is always enough, in any split arrangement and whichever pane held focus before.
- `⌘W` closes the focused pane: the last pane of a tab closes the tab, and a panel window's last tab closes the window. The pane's session keeps running — closing a pane never stops anything by itself.
- The `New terminal` leader shortcut starts a fresh ad hoc terminal session directly and opens it as a new tab: in the main window it lands in the selected workspace's panel, and in a panel window it lands in that window, targeting the focused pane's workspace.
- A workspace panel's `+` button and the new-tab shortcut (default `⌘T`) open the same target picker splitting uses; the chosen or freshly started target opens as a new selected, focused tab, and `⌘T` requires a selected workspace. A panel window's `+` button instead starts a fresh ad hoc terminal session directly with no picker, targeting the focused pane's workspace. `⌘T` does nothing while a panel window is key, or while the picker is already open.
- Built-in terminals use the Spaces-owned theme; changing the appearance updates open terminals without relaunch. Personal Ghostty configuration on the machine — themes, fonts, or any other setting — never affects built-in Spaces terminals.
- Trackpad, mouse-wheel, and touch scrolling works both for terminal-owned scrollback and for full-screen terminal applications that enable mouse reporting. Application scroll events use the gesture location within the visible terminal viewport and the keyboard modifiers active for each event.
- Clicking inside a full-screen terminal application that enables mouse reporting — vim with `set mouse=a`, htop, tmux with mouse mode, lazygit — reaches the application: the click moves its cursor, selects its pane or row, or activates its button. While such an application is tracking the mouse, a click no longer starts a Spaces text selection; holding shift while clicking selects text instead, which is how a selection is made in an application that has taken the mouse. On iPhone and iPad a tap acts as that click while the application is tracking the mouse, and otherwise keeps opening links and focusing the pane.
- Opening a terminal pane does not block the app while remote device credentials are prepared. Spaces opens the pane immediately with an in-pane preparing state, then replaces it with the live terminal when the remote session is ready to render. Repeating a new-terminal action for the same workspace or panel while one is already opening does not start duplicate ad hoc sessions.
- A terminal pane can live in its own panel window: a separate Spaces window holding the same tabbed panel surface, not scoped to one workspace, so its tabs and splits may mix sessions from any workspace or device. Moving a session there removes it from its previous pane — never copies it. Sidebar clicks, numbered shortcuts, and the command palette focus a session wherever its pane lives, including panel windows. Closing a panel window's last pane (or the window itself) closes the window; the sessions keep running, they just lose their panes.
- Panel windows and their frames persist across app relaunch and reopen automatically once the devices their sessions belong to have connected, pruning panes whose sessions are gone; a window whose sessions are all gone does not reopen.
- Explicitly stopping or restarting a workspace closes that workspace's open terminal panes and tracked browser-session tabs after the owning daemon confirms the lifecycle action. Explicitly stopping or restarting a runtime target terminates its session and removes that session's pane (restart relaunches the target as a fresh session, which reopens as a pane when it is next focused). A session that exits on its own — a process crash or error, with no explicit stop — keeps its pane in place showing the final render so its last output stays readable. Because that final render is indistinguishable from a live terminal, such a pane carries a persistent banner naming the state and saying the pane is read-only — "session ended" for a shell that exited cleanly, "session failed" for one that stopped unexpectedly. "Read-only" means the pane refuses input, not that it is frozen: scrolling still works, so the session's earlier output stays reachable by scrolling back through its scrollback. The banner is tinted the same as the target's sidebar row, so the two surfaces reporting the same stopped session always agree. Typing into the pane pulses the banner instead of doing nothing. The banner clears if the session runs again. A pane whose device stops answering stays open the same way, still showing the last frame that device sent, and carries a persistent banner saying the connection dropped and that Spaces is reconnecting. That banner is drawn as an ordinary notice rather than a stopped-session warning, because the session keeps running on the device and the pane recovers on its own; it clears as soon as the device answers again, and a device that stays away is retried progressively less often rather than dialed continuously. Typing into such a pane pulses that banner too, and interacting with it is also how the drop is often noticed first: typing, scrolling, or resizing the pane when it cannot reach the device puts the banner up at once, rather than leaving the pane looking live for the minute or more a silently broken network path takes to be noticed otherwise. Once the banner is up, anything typed is discarded rather than held and delivered once the device answers again, so a command a user gave up on is never replayed into the terminal — including its Enter — minutes later once the link recovers. Input the device refuses for its own reasons — the session is not running, another client owns it — reports nothing about the connection. A session that already ended keeps its own read-only notice while its device is unreachable, since the process is gone whatever the connection does. Starting a target never removes a pane. An ended pane stays open for scrollback only while its runtime entry — the process, coding-agent, or terminal row backing the session — still exists; when that entry is removed, including when the removal happens on another device, the pane closes automatically so it never outlives the readable transcript. Otherwise panes and tabs disappear only through their explicit close controls.
- Ended sessions are retained for seven days after they end, then removed automatically: the runtime entry disappears from the sidebar and device overviews, any still-persisted pane no longer restores, and the transcript is reclaimed on the owning device. If a burst of ended sessions accumulates more than 2 GB of retained session data on one device before the week is up — the transcripts plus the saved final screen each ended pane replays — the oldest-ended are removed early to bring the total back under. An ended pane left open past the retention window closes automatically when its session is removed, the same way it closes when the session's runtime entry is removed on any device. There is no setting for these bounds.
- Switching the selected workspace (including leader-arrow navigation) swaps the right panel to that workspace's panel with its previously selected tab and focused pane restored. Panel layouts — tabs, panes, splits, and the focused pane — persist across app relaunch, reattaching to sessions that are still alive and dropping panes whose sessions are gone.
- While a terminal pane has keyboard focus, ordinary non-⌘ keys (including arrows and ctrl chords) belong to the terminal. ⌘ shortcuts and configured leader shortcuts run app actions first; unclaimed ⌘ shortcuts fall through to terminal-owned ⌘ bindings, and unclaimed non-⌘ leader chords fall through to the terminal pane's normal key handling.
- A key press reaches the running program with its modifiers intact and encoded the way that program asked for: Shift, Control, and Option combine with Enter, Tab, Backspace, Escape, the arrows, the navigation keys, and the function keys, and each combination is encoded against the terminal's current state rather than a fixed table. So `Shift+Enter` inserts a newline in a coding agent that speaks the Kitty keyboard protocol while plain `Enter` still submits, arrows follow a full-screen program's application cursor-key mode, and a program that requested none of this receives the classic sequences. Terminals behave identically here whether the session runs on this Mac or on a remote device. `Shift+Enter` does not submit a line in an ordinary shell, which is how a terminal emulator is expected to behave.
- Right-clicking a sidebar workspace row shows a context menu with the workspace's lifecycle and location actions: Start when it is stopped, or Restart and Stop when it is running; Copy path; Reveal in Finder (local-device workspaces only, since it needs a path on this Mac); Hide, which removes the workspace from the sidebar and stops it first if it is running (the same hide behavior as the Workspace Visibility dialog); and Archive, which runs the same confirmation as the workspace detail overflow menu. A non-git project's standin row offers the same menu for its single workspace.
- Workspace lifecycle controls offer only the actions that apply to the workspace's current state, everywhere they appear: a stopped workspace offers Start alone, and a running one offers Restart and Stop. A stopped workspace never shows a Stop control.
- Right-clicking a sidebar target row shows a context menu with Start, Stop, and Restart (each shown only when the action applies to the target's current state), Rename, and Open in New Window. Open in New Window moves the target's terminal session into its own panel window (enabled only for targets that have a session; browser targets never show it). Rename edits the name inline in the row; Return saves and Esc cancels. Renaming an ad hoc terminal renames its session; renaming a configured process, coding agent, or browser session renames its workspace configuration entry, so a running process picks the new name up on restart.
- Sidebar workspace rows expose a settings action that opens workspace settings in a dialog, like project rows do for project settings.
- The workspace settings dialog matches the project settings dialog: a header with the project and workspace name and a close control, the directory path, then the workspace's configuration sections for Browser sessions, Processes, Coding agents, Services, and Stop script, and a read-only Environment section. Each editable section shows its configured items as rows and expands inline into an edit form when the row's edit control is clicked; the `+ add` header button appends a draft item; every edit saves immediately. The Environment section lists the environment variables injected into every process and terminal of the workspace (the workspace/project identity variables and each service's port/host/URL triple) as a selectable `KEY=value` block the user can select to copy; the values are the authoritative ones the owning daemon computes, so they match what running processes receive. Service rows should show the assigned port number and the derived routed URL as secondary text next to the service name; on a remote workspace whose service is actively forwarded to this Mac, the port shows as `<remote port>:<local forwarded port>` (e.g. `3000:52341`) so the user can see and debug both ends of the forward, while a local workspace shows just its assigned local port. Live port-text refreshes preserve any open service-name draft without committing it. The service-name input is validated as a unique DNS label (lowercase letters, digits, and hyphens, starting and ending with a letter or digit). The dialog is configuration-only: sections show edit and delete controls but no run, stop, restart, or focus actions — runtime control lives on the sidebar target rows.
- The sidebar's Alerts entry shows its title, shortcut hint, and unread count, and is selected like a workspace row when the Alerts view is active. The sidebar's footer strip holds the app identity row: the app name and the devices, settings, and reload actions (plus a warning indicator while another Spaces instance owns desktop control). The right panel owns a footer strip showing the selected workspace's details in one row: a run-state indicator, the workspace name (its git branch, or the project folder name for non-git; read-only — renaming a git workspace's branch changes the name), a runtime warning when something needs attention, the git branch when one is recorded and differs from the workspace name, the directory path (selectable, so it can be copied with `⌘C`), the focused pane's title, and the notes, launch/restart, stop, and overflow actions. The footer stays with the workspace across the panel, loading, and setup views, and clears when no workspace is selected.

## Devices and Pairing
- Every Mac or Linux `spacesd` is authoritative for its own projects, workspaces, configuration, runtime rows, terminal sessions, notes, alerts, paired clients, daemon name, TLS identity, database, runtime files, and workspace filesystem.
- macOS and iOS apps are thin clients over paired daemons. Projects and workspaces are created separately on each device; Spaces does not share workspace records across devices. Each project and workspace has a globally unique identifier so the same repository on two devices is two distinct entries.
- The macOS sidebar lists every paired device at once: the local Mac plus each paired remote device as its own section grouping that device's projects and workspaces. The local device's section header always reads "Local", regardless of the machine's own name; each remote device's header shows that device's stored name. The local device and each remote device load independently, so a slow or unreachable device — including the local Mac when its `spacesd` daemon is down — shows its own loading or offline state without blocking the rest. An offline device header reports the outage through the single control that recovers it — a **Reconnect** button for a remote device, **Restart** for the local Mac, whose own daemon is what has to come back — drawn in the same failed tint the state would be captioned in, with the failure reason available on it; the reason stays current as the outage evolves rather than freezing at whatever failed first. An unreachable device keeps everything it last reported — its projects, workspaces, and their runtime targets — listed for the whole outage, dimmed and naming the device on hover, so they read as its last word rather than live state; its alerts stay in the Alerts list, attributed to the same workspaces, dimmed the same way, and still counted in the alerts badge. A selection under an unreachable device stays selected and its detail pane keeps showing that last-reported state, so an outage never moves the user somewhere else or empties the sidebar under them, and its open terminal panes stay open throughout. An unreachable device can be browsed but not acted on: selecting and expanding its rows, reading its detail pane, opening its settings dialogs, and copying paths all keep working, while everything that needs its daemon — starting, stopping, restarting, hiding or archiving a workspace, running or stopping its processes, coding agents and terminals, renaming a target, creating a workspace in one of its projects, and saving any settings edit — is disabled. Terminals split along the same line: a pane that is already open stays focusable, because focusing it asks the device for nothing and the pane reports the dropped connection itself, while opening a pane for a target that is not open — as a tab, in its own window, or into a split — needs the device's daemon to attach to and is refused rather than leaving a dead pane behind that would not recover when the device returns. Disabled menu items stay listed and grayed rather than disappearing, so a menu keeps its shape through an outage. An action reached another way, such as a keyboard shortcut, is refused with "<device> is offline. Reconnect it and try again." instead of being left to fail against a daemon that is not there. When the device answers again its rows return to full strength in place. An offline device recovers on its own: the sidebar keeps re-checking every device it is not showing as loaded — the local Mac included — so one that comes back returns to normal within seconds without a manual reload. A device that stays unreachable is retried progressively less often rather than hammered. The header's button reconnects that one device immediately instead of waiting for the schedule the repeated failures grew; the section reads "loading…" until the attempt lands, either on the device's projects or back on offline with the reason it failed with this time. It works the same for the local Mac, and reloading the sidebar is never needed to bring a device back. A remote device whose stored credentials are gone reads "Reconnect required" and is offered no button, since it is recovered by pairing it again rather than by reconnecting; that device keeps a plain "offline" caption, because with no button there is nothing else to report its state.
- The iOS client connects to one selected device at a time and shows an add/connect device state when no device is paired.
- Device API traffic uses TLS with pinned daemon identity plus a per-client full-control token. Clients reject endpoint identity mismatches before sending authenticated requests.
- `spaces device pair` with no source opens a short-lived pairing window on the same-machine daemon and prints `spaces://pair?...` details for terminal-driven iOS pairing. The Mac Devices settings section shows QR codes for pairing iPhone and iPad clients with any device already connected to the Mac client, listing which of the daemon's addresses the code carries.
- A pairing link carries an ordered list of the daemon's reachable addresses, most-preferred first. A client races candidates in that order and stays on whichever one answers first, preferring the daemon's local-network address and falling back to its Tailscale address when the client is away from that network; if none answer, the client is told so and pointed at Tailscale as the likely fix. The iOS client re-prefers the local address when the app returns to the foreground.
- A client also learns a paired device's current addresses each time it connects, independent of the pairing link: this is how a device paired before its Mac had Tailscale gains the tailnet fallback the moment the Mac gets one, with no rescan required. The iOS paired-device list shows which network path a device's active connection is using ("Local network" or "Tailscale") alongside its address.
- Pairing is version-gated. The pairing link carries the daemon's wire-protocol version and app version; the redeeming client refuses an incompatible link before consuming the one-time window, and the daemon symmetrically rejects a client whose wire-protocol version differs before validating the code. Either side tells the user to update whichever end is older.
- Pairing stores the pinned daemon identity and client token in Keychain. Client SQLite backup files contain paired-device metadata only and do not contain pairing tokens. Pairing the same daemon again updates its existing paired-device entry rather than adding a second one.
- Pairing a remote device for macOS asks for the SSH host, with the optional username (defaults to the SSH login) and port (defaults to 22) kept under an "Advanced" disclosure, validates SSH with `BatchMode=yes` and `StrictHostKeyChecking=yes`, runs `~/.spaces/bin/spaces device pair --json` on the remote device, then pairs with the Device API at the effective OpenSSH `HostName` and returned API port. When Spaces is not installed on the remote device, pairing fails with install guidance: a Mac is directed to install the Spaces app, while an Ubuntu 24.04 device shows the version-pinned install command as a selectable block with a copy button, plus an "Install Spaces over SSH" action that runs the installer on the device over the same SSH connection — showing an in-progress state for up to several minutes — and pairs automatically on success. Missing or failing SSH is a setup failure for pairing, browser forwarding, and editor opening. Remote terminal sessions do not depend on SSH.
- Paired clients have full control of every daemon they are paired with. Paired-client administration is handled by daemon control paths rather than shown as a normal client screen.
- Creating projects, workspaces, terminals, processes, and coding-agent runs targets the daemon that owns the affected row: on macOS that is the device of the selected project or workspace, and on iOS it is the selected device. Reveal-in-Finder is available only for local-device workspaces, while opening the preferred editor works for both local- and remote-device workspaces. Project creation accepts a daemon-side Git URL or an existing daemon-local path.
- The `spaces` CLI targets the same-machine daemon by default for project, workspace, and agent commands, and accepts `--device <name-or-id>` on the commands an orchestrator needs to discover and prepare work on a paired device: `project list`, `workspace list`, `workspace create`, `workspace start`, and `workspace restart`. `project list`/`workspace list --device` read the device's overview, so `workspace list --device` shows only active workspaces and rejects `--include-archived`. `agent signal` has no `--device` route: an orchestrating agent may read a peer's status but must not forge it on another device.
- The CLI and MCP server are Device API clients for terminal access across devices: `spaces terminal list`, `spaces terminal send text`, `spaces terminal send bytes`, and `spaces terminal tail` accept `--device <name-or-id>` to target a paired device's sessions, and the matching MCP tools accept an optional `device` argument. Omitting the device targets this machine's local sessions. Remote send and tail are token-authorized without terminal attachment, so orchestrator agents can drive sessions they never render.
- `spaces device pair` opens a pairing window on this device when given no source, pairs the CLI's profile with another device's daemon over SSH (`--ssh user@host`, which fetches the remote device's pairing link over SSH and redeems it), or redeems a `spaces://pair` link (`--link`). `spaces device list` shows paired devices and `spaces device remove` deletes a pairing and its stored credential. The CLI shares the Mac app's per-profile client identity, paired-device records, and credential store, so devices paired from either surface are usable from both.
- Remote terminal attach opens a local pane attached to the remote daemon session over the authenticated Device API, and needs no SSH to that device. Remote browser sessions that target a daemon-local service open through an SSH local forward. Remote editor actions open the daemon worktree through the configured SSH-capable editor, which presents the remote worktree as a local window. Re-opening the editor for a workspace focuses the editor's existing window for that folder instead of opening a duplicate. Opening a remote workspace needs an SSH-remote extension in the editor; when the editor lacks one, Spaces offers to install it before opening.
- Each device stores workspaces under its own workspace root by default. The default root is `~/spaces/workspaces/` for installed macOS and Linux daemons, with app-managed git clones under `~/spaces/repos/`.

## Workspaces

### Creation
- Users can create, update, focus, stop, restart, and archive workspaces from the GUI.
- The CLI should expose `spaces project list`, `spaces workspace list`, `spaces workspace create --project <id> --branch <branch>`, `spaces workspace start --workspace <id>`, `spaces workspace restart --workspace <id>`, `spaces device pair`, `spaces device pair --json`, `spaces device list`, `spaces device remove`, `spaces agent signal <event>`, `spaces terminal list`, `spaces terminal command`, `spaces terminal send text`, `spaces terminal send bytes`, `spaces terminal tail`, `spaces terminal show`, and `spaces mcp`.
- `spaces mcp` runs a Model Context Protocol stdio server that an MCP client such as Claude Code, Codex, or opencode launches and drives. It exposes project, workspace, terminal list/tail/send, and paired-device list tools. Terminal send accepts either UTF-8 text or explicit byte values, and the terminal tools, the project/workspace list tools, and `spaces_workspace_create`/`_start`/`_restart` accept an optional paired-device selector. Agent lifecycle signals are CLI-only hooks so coding-agent shell integrations can report explicit events without making those hooks available as agent-callable MCP tools.
- `spaces import` is not a public command. Workspace creation must be explicit about project and branch because registering a workspace creates daemon state, allocates runtime resources such as ports, and can run setup work.
- Workspace start, restart, and stop actions target the active daemon. Terminal commands should support listing available sessions by session ID, runtime state, and working directory and printing a clear empty-state message when none are available, sending UTF-8 text, sending decimal byte values, tailing recent output, and opening native Spaces-owned session windows in owner-seeking mode.
- App-launched built-in workspace terminals, process windows, and coding-agent windows should be owned by the per-user `spacesd` daemon and reopen onto the same live shell session across `SpacesApp` quit and relaunch.
- Quitting `SpacesApp` while service-owned terminal sessions are running should prompt the user to quit while keeping sessions running, stop all sessions and quit, or cancel. Keeping sessions running is the default.
- Stop All and Quit is an explicit clean stop for the local Mac daemon. Local workspaces return to stopped through the normal workspace stop behavior, configured processes and coding-agent launchers return to not started without exited-process alerts, ad hoc terminals are removed, and Spaces-tracked browser-session tabs are cleaned up without closing unrelated user tabs or windows. The action does not stop paired remote-device workspaces. If the clean stop cannot complete, Spaces offers Force Quit to terminate the remaining terminal sessions and quit, or Cancel Quit to keep the app open.
- `spaces terminal` sessions should remain owned by a per-user `spacesd` daemon so they can survive `SpacesApp` quit and reopen against the same live shell session as long as the service remains alive and the session lifetime is still valid.
- `spaces terminal command` targets a workspace — an explicit `--workspace <id>` or, when omitted, the deepest workspace whose directory contains the current directory (erroring clearly when neither resolves) — and opens at that workspace's directory with its full environment, the same as the app's `New terminal`. It creates a persistent ad hoc terminal session in that workspace, appears in the app's workspace terminal list, remains discoverable through `terminal list`, is controllable through the terminal CLI, and is stopped by workspace Stop, workspace Restart, and Stop All and Quit.
- The spacesd daemon should start the first-party Device API listener on launch, keep a stable endpoint while it is running, and advertise nearby pairing metadata with Bonjour when the platform supports it.
- The Mac user settings open as a floating dialog window with a two-panel layout: a header bar with the Settings title and a close control, a left navigation list of General, Shortcuts, Devices, and MCP sections, and the selected section's content in the right panel. The dialog floats over the main window, leaving the current sidebar selection and detail pane untouched. The Devices section lists connected daemons, includes the local Mac daemon when it is available, lets the user choose the active daemon for the home surface, offers a per-device QR pairing window for iPhone and iPad clients, and includes an SSH target form for connecting this Mac to a remote daemon. Ended rows are read-only, skip attach, takeover, input, resize, and reconnect loops, and show the persisted final Ghostty render when one is available.
- The iOS terminal detail view should keep a stable height across owner preparation, takeover, and ready states so status changes do not resize the terminal viewport after ownership handoff.
- The iOS terminal detail view should show the selected process, coding-agent, or workspace-terminal row name when the session maps to a workspace runtime row. Runtime lifecycle controls should live behind a `...` menu with run, restart, and stop actions when available.
- The iOS terminal keyboard accessory should use a toolbar: the scrollable key strip is ordered `tab`, `/`, `~`, `|`, `-`, `_`, `esc`, `shift`, `ctrl`, `cmd`, `opt`, and a compose button; a single arrow-key joystick and the keyboard hide/show control remain fixed, in that order. The joystick is a relative thumbstick: the touch-down point is neutral, so sliding the finger toward a direction sends that arrow key and holding the slide repeats it so the cursor moves many steps, while a stationary tap sends nothing. Modifier keys apply to the next compatible text, arrow, Return, or Backspace input for terminal line-editing chords, so `shift` then Return sends `Shift+Enter` on a device with no hardware keyboard, and `cmd+k` clears the terminal-owned screen and scrollback. A hardware keyboard sends modified Return and `Shift+Tab` directly.
- The iOS terminal viewport should use the available terminal width and size to the visible render area above the software keyboard and accessory toolbar so bottom rows and the prompt remain visible with long terminal content.
- iOS terminal scrolling should follow touch movement proportionally, with small swipes producing small precise scroll changes instead of discrete one-row jumps, and should deliver swipes to mouse-aware full-screen terminal applications at the touch location.
- iOS terminal taps should open Ghostty-detected links before applying tap-to-focus behavior. Readable Mac file paths exposed by the paired bridge and direct HTTPS URLs preview inside Spaces rather than opening in another app: raster images, video, and PDFs preview in QuickLook; plain text files preview in a selectable viewer; Markdown files preview rendered by default with a toggle to view the raw source; HTML files preview in an in-app web view scoped to that single file, so sibling assets referenced by relative paths and absolute network subresources do not load. Any other web link, including a plain web page, also opens in that in-app web view with an Open in Safari action and normal web networking; every file-backed preview offers Share instead. Text, Markdown, and HTML previews over 4 MiB are refused with a message. A loopback address (e.g. `localhost`) printed by a remote session shows a notice that it isn't reachable from this device instead of attempting to preview it.
- The iOS terminal compose button should open a message composer sheet where the user writes a multi-line message and attaches images — a staged screenshot or an image from the clipboard — before sending. Sending submits the message as one owner-input burst: the typed text, then each image as a daemon-local file path, then Return, so trailing image paths read as arguments to the typed text. The composed text and inserted image paths use terminal paste semantics before the final Return; in bracketed-paste-aware programs, multiline draft text is not submitted line-by-line before that Return. The composer sends typed text verbatim without autocapitalization or autocorrection. Images paste through the paired daemon the same way as macOS image paste, accepting common formats and rejecting images over 10 MiB. The composer requires the same owner-interactive readiness as typing. Composer text and attachment controls are disabled while a composed send is in flight. If any step fails, Return is not sent and the whole draft is kept so the user can retry; text, image, and submit failures use step-specific error text, while authentication or ended-session failures route through the normal terminal-input recovery flow. A successful send clears the sent draft. The draft survives closing and reopening the composer.
- Ad hoc built-in terminal windows opened from Spaces, including the `New terminal` shortcut path, should remain listed in the sidebar's runtime-target list even before their native window ID has been backfilled.
- Opening a built-in `Spaces` terminal from the app should not block the sidebar window while the session backend becomes ready; session bootstrap latency may still exist, but the workspace UI should stay interactive during that wait.
- Opening a local built-in `Spaces` terminal window from a reserved workspace-terminal session should present immediately with a preparing state while the shell and live renderer become available. Input and terminal controls remain disabled until the session publishes control and subscription availability.
- When Spaces focuses an already-open built-in process window from the normal workspace flow, the owner attachment should still belong to that client and remain ready for input without restarting the session.
- Configured process and coding-agent rows should have one current Spaces terminal session identity shared by Mac and iOS. Launch, focus, restart, and mobile overview paths should reuse that identity while it is current instead of creating duplicate configured rows or duplicate terminal sessions for the same configured slot. Configured rows remain visible after their process exits when they have a terminal identity, so Mac and iOS can open the ended session's final render instead of hiding the configured slot.
- Restarting a configured process or coding agent should replace the previous Spaces terminal identity cleanly: if the old native window is still open, Spaces should claim it for the replacement session or close it before the replacement becomes the current running session, so an exited configured window does not remain beside a running replacement.
- A terminal session may have one active owner client and one or more non-owner viewer attachments recorded at the same time.
- Closing a process or coding-agent built-in terminal window detaches that native window while preserving the runtime and session identity for later focus. Closing an ad hoc workspace terminal window terminates its service-owned terminal session. Stopping a workspace also terminates ad hoc built-in terminal sessions owned by that workspace.
- The process Spaces starts for a terminal session does not outlive that session. A session ends when its terminal does — when the command exits, or when it gives up the terminal by closing its standard input, output, and error while continuing to run — and in the latter case Spaces stops that process as part of the teardown rather than leaving behind a running program the user can no longer see or stop.
- Ad hoc built-in terminal sessions should stay alive while any local client or recently active remote/device client remains attached and should clean up once the final live attachment detaches or expires unless the user explicitly closes the terminal window or stops the workspace.
- Only the active owner client may send input or resize the terminal; stale owners and stale resize events are ignored.
- The Mac app should remain alive while it coordinates native windows or client-driven terminal ownership changes even if the main window is hidden or the app is backgrounded.
- Live non-owner terminal windows on macOS and iOS should show takeover and status UI instead of terminal content. The macOS viewer window presents a status message plus a Take Over action rather than the full session detail stack. If the session has already ended and a final Ghostty render is available, that final render may still be shown with an indication that the terminal has ended.
- The New Workspace form opens in its own dialog window with the same header as the Settings and New Project windows, dismissed with the close button, Cancel, or `Esc`.
- For git projects, the new-workspace form shows three inline inputs with no advanced section: branch (create-branch or use-existing mode), base branch, and notes. There is no separate title or directory-name input.
- Git workspace creation must require an explicit branch choice. `Create branch` must reject any branch name that already exists, while `Use existing` is the only path allowed to attach or revive a workspace on an existing branch.
- The checkout directory name for a git workspace is generated automatically as a non-conflicting managed directory name, decoupled from the branch name; it is not user-editable.
- A git workspace's display name is its branch, and a non-git workspace's display name is the project folder name; there is no separate, editable title. Git branch identity determines whether a workspace is revived or conflicts with an existing archived record. An archived record holds that identity only for as long as its branch exists: once the branch is gone — deleted while archiving, or merged and deleted outside Spaces — the branch name is free for a new workspace, and the archived record stays as history under its checkout directory name.
- Archiving a git workspace should offer optional local-branch and remote-branch deletion checkboxes so the user can clean up branch names when the workspace is no longer needed.
- Workspace creation should feel fast in the GUI: once the workspace record and directory exist, the New Workspace form dismisses and selects the new workspace immediately rather than waiting for the setup script. A long-running setup script then runs in the background and its progress streams in the selected workspace's setup screen.
- Workspace settings used for launch must remain editable after creation.

## Launch and Runtime Behavior
- Launch starts the workspace's configured processes and captures the resulting windows.
- Browser sessions stay configured while the workspace is running, but Spaces should leave them unopened until the user explicitly focuses that browser session.
- Unopened browser sessions should not degrade runtime health or show missing-window warnings for an otherwise running workspace.
- Configured processes that have never been started, or that were explicitly stopped by the user, should remain idle and directly runnable without degrading runtime health or creating Alerts attention.
- Closing a process terminal window leaves the process running. If a tracked process window becomes stale while the process remains alive, Spaces should recover the terminal view and reattach when the user opens a new window for it.
- Workspace titles and tracked-process names are user-controlled text. They may contain visible separator-like substrings without breaking window creation, listing, or focus recovery.
- Editing workspace settings while a workspace is already running must not start or stop browser sessions or coding agents as part of save-time reconciliation. Process name and on-exit edits should update tracked running processes immediately, while command edits should require explicit confirmation to restart the affected running processes; canceling that prompt should leave the existing process configuration unchanged. New configured rows should appear immediately with their non-running status so the user can decide what to open or recover.
- Process commands run as terminal-style shell command strings through the user's resolved login shell.
- Process commands support normal shell behavior such as environment assignment, `cd x && y`, pipes, redirection, command substitution, and shell expansion.
- Every command Spaces runs in a terminal — configured processes and coding-agent launchers, an ad hoc `spaces terminal command --command`, and a spawned coding agent — runs inside an interactive login shell, so user shell PATH and tool initialization are available to commands such as `claude`, `codex`, or `opencode` wherever they are installed. A command resolves exactly what it resolves when typed into a Spaces terminal.
- Configured coding-agent rows should support direct run, stop, and restart controls. Stop should close the tracked native terminal window when present, terminate the backing built-in terminal session, remove runtime state, and keep the configured launcher available. Restart should relaunch configured or claimed launcher rows and report a clear unsupported action for unconfigured live agents.
- Terminal panes carry no runtime controls of their own; start, stop, and restart for the pane's process, coding agent, or ad hoc session live on the sidebar target rows' context menu. Kept-open exited terminals keep showing their final render and stay stoppable/restartable from the sidebar while the configured row still exists.
- App-level configuration is changed in the app only, not through `spaces`.
- The project and workspace editors validate process commands when they are saved. Process commands must be non-empty.
- Stop shuts down tracked runtime state and closes tracked browser-session tabs safely.
- Restart performs a stop followed by a fresh launch.
- `workspace start` is the idempotent "ensure running" path:
  - if stopped, it launches the workspace
  - if running, it restores failed or exited runtime
- `workspace restart` forces a full restart
- Launch should wait for setup to finish and should surface setup failures clearly.
- Workspaces with setup `pending`, `running`, or `failed` show a setup recovery screen instead of normal workspace detail controls.
- The setup recovery screen shows setup status, timestamps, exit code, error text, and the setup log tail. It allows setup retry, Finder reveal, ad-hoc terminal access, and setup log copy/open actions. Failed setup also exposes inline setup script editing before retry.
- Configured processes, coding-agent launchers, and browser sessions must not launch or recover until workspace setup has succeeded. Ad-hoc workspace terminals remain available for setup repair.
- If a configured process exits during startup, launch should surface the recent process output itself and should not open a secondary recovery window that only reports a follow-on attach failure.
- A project declares named services. Each service is a unique DNS-safe name (lowercase letters, digits, and hyphens, starting and ending with a letter or digit, up to 63 characters) and receives one dynamically assigned local port per workspace.
- Each workspace process, setup script, and stop script runs with service and workspace environment variables available:
  - `SPACES_<SERVICE>_PORT` — the assigned local port for that service, uppercased with hyphens turned into underscores (service `admin-ui` is exposed as `SPACES_ADMIN_UI_PORT`).
  - `SPACES_WORKSPACE_SLUG` — a DNS-safe per-workspace slug, such as `login-fix-a3f9c2d1847b`. Git workspaces use the branch name as the readable slug prefix; non-git workspaces use the project name.
  - `SPACES_<SERVICE>_HOST` — the routed hostname `<service>.<slug>.localhost` for that service, without scheme or port, for framework host allowlists.
  - `SPACES_<SERVICE>_URL` — the routed URL `http://<service>.<slug>.localhost:7391` for that service. Reference this directly (for example `$SPACES_WEB_URL`) instead of composing a URL by hand.
- A process binds the port Spaces assigns it, for example `PORT=$SPACES_WEB_PORT npm run dev`.
- A bundled Caddy reverse proxy runs on the Mac and routes `http://<service>.<slug>.localhost:<router port>` to the service's Mac-local upstream, so every workspace reaches its services at stable per-workspace URLs. The router port is `7391`; there is no user-facing setting to change it. Routing is plain HTTP on that shared high port, listens only on loopback addresses, and requires no TLS, certificate, or administrator setup because Chrome and Safari treat `*.localhost` as a secure loopback context. Chrome is the supported browser; Firefox does not resolve arbitrary `*.localhost` names by default. Caddy routes every service host whether or not the service has a browser session.
- Local workspace service routes point directly at the service's assigned `localhost` port on the Mac, so service processes can bind either IPv4 or IPv6 loopback. Remote and Linux daemons do not run the Caddy router; when the Mac app observes a running remote workspace with named services, it starts one SSH local-forward process for that workspace with one Mac-owned ephemeral binding per assigned service port and registers Caddy routes to those Mac-local forwards. Focusing a remote browser session that targets a named service reuses the workspace's forward when it is ready and opens it on demand when needed.
- Remote and Linux workspace processes receive `SPACES_<SERVICE>_URL` so app servers can allowlist the browser-facing host or origin for CORS and framework host checks.
- Adding a service from the workspace settings dialog should reserve its port number immediately instead of waiting for the next workspace launch.
- Service assignments belong to the workspace until that workspace is archived. Stopping a workspace must not give its assigned port numbers back to other workspaces.
- When a stopped workspace owns services, Spaces may hold placeholder reservations for those ports, but starting any workspace runtime releases those placeholders so user-facing servers can bind normally. While the workspace is running, assigned service ports are not placeholder-reserved; users resolve conflicts manually if another local process claims an assigned port before the intended server binds it.
- Stopping or restarting a workspace must never close unrelated user windows.
- Runtime health is separate from lifecycle state:
  - `Running` workspaces can be healthy or degraded
  - `Stopped` workspaces can still have stale tracked runtime leftovers that need cleanup or recovery

## Window Management and Focus
- Workspaces map to tracked focus targets: terminal panes and browser-session tabs in tracked Chrome windows.
- Spaces should focus the correct window or workspace quickly, even when switching across apps.
- Browser focus should match the intended browser session by URL, not by window title.
- When focusing a browser session, Spaces should first try the tracked Chrome window, then scan all Chrome windows for a tab whose URL matches the session so a user-moved tab can be adopted. If the session is not open, Spaces should open it as a tab in an existing tracked workspace Chrome window when one is available, otherwise in a new Chrome window.
- When browser-session URLs overlap by prefix, Spaces should prefer the exact target URL and avoid matching a longer sibling session URL during prefix fallback.
- Terminal focus should land on the intended dedicated process or agent session.
- After the GUI focuses or opens an external window, Spaces should hide itself immediately so the target app stays unobstructed.
- When a workspace detail view becomes visible, Spaces should refresh workspace windows and process state asynchronously so stale rows reconcile shortly after the page appears.
- If tracked windows become stale during next/previous window cycling, Spaces should skip them and continue to the next live target.
- Spaces should not poll in the background to verify whether a tracked browser-session window still exists; it should validate that on demand when the user focuses that browser session.
- If direct window focus from the app targets a stale browser session, Spaces should adopt an existing matching Chrome tab or reopen that session in a tracked workspace Chrome window and update tracking without showing an error modal first.
- If direct window focus from the app targets a stale process window, Spaces should first try to recover silently by reopening the built-in session when the process is still running. If the process is no longer running, Spaces should show a modal warning with `Recover (Cmd+R)` and `Cancel (Esc)`, and the explicit recovery action should restart it inside the built-in terminal.
  - coding-agent windows only show the error state and do not offer recovery
- Spaces should still reconcile stale tracked windows in the background instead of forcing the user to repair state manually.
- Degraded runtime health should appear as a warning on top of the current `Running` or `Stopped` lifecycle state, not as a separate replacement state label.

## Alerts and Health
- The app should surface attention items across workspaces in one place.
- On macOS the Alerts list and badge aggregate attention items across every paired device, so a single combined badge reflects work needing attention on the local Mac and on remote devices together. Remote attention items are derived from each remote device's overview.
- Attention includes exited processes and coding-agent states such as blocked or done.
- A terminal bell raises an alert for the session that rang it, so a long build or a program asking for something is noticed from anywhere in the app. The alert is raised only when the user is not looking at that session: a bell that rings while the terminal has keyboard focus on the Mac, or while its session is open in the iOS terminal viewer, is heard by the user directly and raises nothing. Opening or focusing a session does not clear the alert for a bell it rang earlier, while the user was elsewhere — that one waits to be dismissed like any other. Repeated bells from the same session within a short window are one alert rather than a stream, and the alert is dismissed like any other; a bell after that window has passed raises it again.
- A stopped workspace can still contribute attention items when that helps the user notice something actionable.
- Alerts rows should support direct window focus by click and by the numbered window shortcuts.
- The Alerts sidebar badge and dock badge should reflect the number of visible Alerts attention rows after dismissals are applied.
- Users should be able to dismiss individual Alerts attention items so they disappear from the Alerts list and dock badge until that specific attention event changes.
- Dismissing an Alerts attention item must not hide the underlying process or agent row from the sidebar's runtime-target list.

## Editing and Shortcuts
- The app should support keyboard-driven use for common actions.
- Global shortcuts should bring Spaces forward and support fast workspace switching.
- The global app-toggle shortcut should hide Spaces when it is already frontmost and visible, and show it otherwise.
- The app should expose a separate global command-palette shortcut that opens a lightweight palette without unhiding or fronting built-in terminal windows.
- The command palette should default to `Cmd+Opt+-`.
- Summoning Spaces from the global app-toggle shortcut should raise only the main window above other apps and onto the active space.
- The global app-toggle shortcut should depend only on whether the main Spaces window is visible. Built-in terminal windows and the command palette must not change whether `Cmd+Opt+=` shows or hides the main window.
- The command-palette shortcut should depend only on whether the command palette is visible. The main window and built-in terminal windows must not change whether `Cmd+Opt+-` shows or hides the command palette.
- When Spaces is summoned, it should select the workspace for the window that was focused immediately before activation when that window belongs to a tracked workspace; otherwise the view stays on whatever pane was already visible, so summoning never switches the view without that explicit signal.
- The app should expose a configurable shortcut leader that supplies the shared modifiers for leader-based shortcuts like workspace navigation, Alerts, editor, terminal, and Finder. A shortcut leader must contain at least two modifiers.
- Moving the sidebar selection (Alerts and workspaces) up or down is bound solely to the configurable leader+up/leader+down shortcuts (Next workspace / Previous workspace); plain up/down arrows never move the sidebar selection, so there is a single navigation path. This sidebar movement stays a separate concern from global next/previous window cycling.
- Leader+up/leader+down move the sidebar selection even while a terminal pane has keyboard focus and owns the plain arrow keys; a matched chord is consumed even at a list edge so it never leaks into the terminal.
- The command palette should draw from every navigable workspace target that can appear in the sidebar's runtime-target rows: browser sessions, processes, ad-hoc windows, configured coding-agent launchers, and live coding-agent terminals.
- When the command palette opens with an empty query, it should show Alerts attention items first and then the most recently focused targets across workspaces, capped to the first nine visible rows. If there is no recent focus history, it should fall back to the existing workspace-target order.
- Command-palette rows should show the same status language used by the sidebar's runtime-target rows, including process state and coding-agent state.
- Once the user types a query, command-palette search should fuzzy-match across all workspaces using the workspace display name (branch, or folder name for non-git), target name, and secondary detail text, including compact cross-field queries such as `fu` matching `Frontend` plus `URL`.
- The first command-palette result should stay selected by default, arrow keys should move the selection, and `Enter` should execute the same target-level focus/open action used by the numbered window shortcuts.
- Leader-based previous/next window cycling should follow the most recently focused targets within the workspace rather than the static workspace definition order. Each repeated cycle sequence should traverse a frozen ordering snapshot so `previous` and `next` walk the full target set instead of bouncing between the last two windows.
- Leader-based next/previous window cycling should always mean window cycling, even when the main Spaces window is focused.
- Leader-based previous/next window cycling should include only already-open workspace windows: browser sessions whose resolved URL is present in their tracked Chrome window, and terminal-backed process, ad hoc terminal, and coding-agent targets whose Spaces pane is open. Direct browser-session focus updates tracking when it adopts a user-moved tab, so cycling follows that tab after focus. Unopened browser sessions, not-yet-running configured processes, configured agent launchers, and terminal sessions without a pane stay available through direct focus but are skipped by cycling.
- Window rows in the selected workspace should expose numbered shortcuts for direct focus.
- Numbered window focus shortcuts should keep the saved workspace-settings order for configured browser sessions and processes, and append newly added ad-hoc windows after those configured rows.
- Window focus actions and numbered shortcuts should follow one target-level rule: make that target available immediately.
- Focusing a target from the app UI or command palette should keep Spaces visible instead of hiding the app after the target receives focus.
- The global `Toggle app` shortcut controls only the main Spaces window, not the built-in terminal windows or the command palette. If a built-in terminal or the command palette is focused, toggling the app should bring the main Spaces window forward instead of fronting all Spaces-owned windows.
- The global command-palette shortcut controls only the command-palette panel. Showing the palette should not hide the main window, and hiding the palette should return focus to whichever window was active before the palette was shown.
- Returning to the main Spaces window from a focused built-in terminal should show the workspace detail view that owns that terminal, matching the behavior of externally hosted terminal windows.
- If the main Spaces window was summoned from a focused built-in terminal, toggling the app again should hide only the main window and restore focus to that same built-in terminal.
- If the main Spaces window was summoned from an untracked external app such as Chrome, toggling the app again should hide only the main window and return focus to that external app instead of leaving Spaces frontmost.
- A live target should receive focus. A configured target that is not live should be opened directly instead of requiring a full workspace launch or restart.
- Opening a configured browser session, process, or coding agent from a stopped workspace should move that workspace out of the stopped state immediately.
- Partial runtime is a first-class workspace state: some configured targets may be live and focusable while others remain directly openable.
- Window focus actions must operate on one target only and must not route through full-workspace `Launch` or `Restart` semantics.
- Starting one configured process must not create Alerts attention for sibling configured processes that were never started or were explicitly stopped. Those rows should stay directly openable in place and reuse the same configured row instead of creating duplicates.
- Starting or restarting one configured process or coding agent should not leave a second configured instance visible on Mac or iOS for the same workspace slot. Ad-hoc terminal sessions may remain visible only when they are not represented by a configured process or coding-agent row.
- Alerts rows should show the tracked window or process name as the primary label and the target detail, such as a browser URL or process command, as secondary text.
- Ad-hoc terminal rows should keep their generated focus name as the primary label and use the live terminal window title as secondary text.
- Production CLI-driven focus is not part of the `spaces` command surface.
- Harness-driven focus should use unique names across focusable browser sessions, processes, and coding-agent terminals when it needs to exercise focus behavior.
- Configured workspace processes and browser sessions must always have explicit names; Spaces should reject unnamed entries instead of falling back to commands or URLs as identities.
- Focus target discovery may remain GUI-centric; the production CLI does not need a separate read-only discovery command.
- `spaces terminal tail` should reconstruct the visible terminal screen from persisted session output using the session's last known terminal size, so wrapped lines and full-screen terminal redraws stay aligned with the live session after resizes.
- `spaces terminal tail` should keep showing a running session's screen for as long as the session lives, however the running program chooses to redraw. A full-screen program that paints its frame once and then updates it in place must stay readable — an orchestrator confirming a child agent's progress must never be handed blank output for a session that is working.
- `spaces terminal tail --lines <n>` should return the last `n` lines of a session's history when the session has that much, not only the lines currently on its screen. A scrolling session (an ordinary shell) keeps its scrolled-off output available up to the session's retained transcript; a full-screen program that keeps its output on one screen has no history above that screen and returns what it has. Tail is an orchestration command rather than an interactive one: it reads a session's whole retained transcript, so its cost grows with that transcript up to the retained bound, and a tail of a very long-lived session takes noticeably longer than one of a fresh session.
- `spaces terminal tail` should report what the session's terminal actually retains, matching what scrolling that pane would show. Output a program cleared off the screen with a full-screen erase stays in the session's scrollback, so it stays available to tail; only output the program erased from the scrollback itself, or that the retained-transcript bound dropped, is gone.
- For sessions Spaces identifies as coding agents, terminal tail output should omit a faint inline suggestion that begins at the visible cursor, including its soft-wrapped continuation. Ordinary terminal sessions should not apply this filter. Real input, status and model lines, tips, dialogs, autocomplete menus, and faint text outside that cursor-start run should remain visible even when they appear after or below the cursor.
- Window-number shortcuts should use a configurable direct-focus modifier plus digits `1` through `9`.
- Shortcut handling must not break normal text-edit shortcuts while an input is focused.
- Recovery affordances should reserve `Cmd+R`; app-data reload should default to leader+`R` so it stays distinct from recovery modals.
- Alerts should default to leader+`A`.
- Opening the new-tab session picker should default to `Cmd+T`.
- Every keyboard shortcut the product supports must be configurable from the GUI settings panel.

## Coding-Agent Integration
- Coding agents can explicitly report lifecycle events through `spaces agent signal <event>`. The command reads the workspace and terminal-session IDs from `SPACES_WORKSPACE_ID` and `SPACES_TERMINAL_TRACKING_ID`, accepts explicit `--workspace` and `--session` overrides, and exits successfully without reporting an event when neither CLI arguments nor environment provide both IDs. Supplying one ID explicitly without the other fails with an error, because a caller that names a session meant to signal for it.
- Agent status events are not implied by workspace creation, `start`, or `restart`, but workspace launch should open any configured coding-agent rows so they appear alongside runtime-managed agents under one `Coding Agents` section.
- `spaces agent signal` should support explicit `init`, `working`, `blocked`, `done`, and `exit` events.
- `spaces agent signal` from a Spaces-managed terminal should update the owning daemon database for the workspace that owns the session.
- Agent events that cannot be reliably attributed to a terminal must be dropped, not guessed onto the frontmost window.
- `init` should identify the originating terminal and either attach to an already tracked terminal row or create a new tracked terminal row for that coding agent.
- Non-`init` signal events should update the existing agent row for the originating terminal. If no agent row exists, the event may establish one only when the signal context or current terminal runtime identifies the terminal as a coding agent; otherwise the event should be ignored.
- Coding-agent rows should render after browser and process rows so non-agent shortcut ordering stays stable when agents appear or disappear.
- Configured and ad-hoc coding agents should share the same `Coding Agents` section rather than rendering as separate launcher and runtime sections.
- A Spaces-owned ad-hoc built-in terminal can appear in `Coding Agents` when its live foreground process is a known coding-agent command such as `codex`, `claude`, `claude-code`, or `opencode`. Once an agent row exists for that terminal session, foreground process changes do not demote or relabel it.
- A signal-established ad-hoc agent row should remain in `Coding Agents` for its live terminal session even if the foreground process is a shell, wrapper, unknown command, or another known agent command. A live `spaces agent signal ... exit` records the session as exited instead of demoting it; Stop, terminal-session exit, and terminal cleanup own removal or completion. A later `init` in that same terminal (a new agent reusing it) resets the row from exited back to idle.
- Foreground process detection should not infer lifecycle state. `spaces agent signal` remains the source for agent status such as spinning, blocked, done, and exit.
- A blocked agent returns to `working` when it resumes after the human or an orchestrator answers its permission prompt. opencode reports the answer itself, so its row leaves `blocked` the instant the prompt is allowed or rejected. Claude Code and Codex report no such event and fire their pre-tool hook *before* the permission decision, so for them the agent leaves `blocked` when the approved tool finishes running — a long approved command keeps the row `blocked` for as long as it runs. Cancelling a Claude Code permission prompt aborts the turn with no hook at all, so that row stays `blocked` until the human sends its next prompt. Repeated `working` signals from an agent that is already working are suppressed — they add no lifecycle events and do not refresh the row's updated time, which continues to mark when the agent entered its current status.
- Every tracked window row should have a unique visible name within its workspace. Two coding-agent rows must not share the same name.
- Configured coding-agent launcher names are reserved within the workspace. An ad-hoc coding agent detected with the same label should be auto-renamed with a numeric suffix instead of colliding with the configured launcher slot.
- Launching a configured coding agent is idempotent for its reserved slot: if that coding agent still has a live tracked terminal, Spaces should keep the existing row instead of deleting and recreating it.
- Focusing an ended configured coding-agent row that still has a Spaces terminal identity should focus the ended session and its final frame instead of launching a duplicate. Launching a replacement belongs to an explicit launcher or restart action.
- `working` should show activity, `blocked` should show a warning and count toward Alerts and dock attention, and `done` should remain in Alerts and dock attention until dismissed while still indicating completion on the workspace row. `idle` should show no activity indicator and create no Alerts attention. `exited` is a distinct status — the agent process is gone but its terminal survives — shown with a dimmed hollow indicator and, like idle, creating no Alerts attention and counting as not active.
- `exit` should mark the row exited when the terminal is still open, so a status change (rather than a disappearing row) reports the exit and any cross-device watcher's held blocked line is withdrawn; if the terminal is closed, ad-hoc agent rows should be removed immediately, including when background runtime refresh detects the terminal closure after the fact, while rows linked to workspace process terminals should remain idle. A configured coding-agent launcher's row instead records done on exit (its slot stays visible for the ended session's final frame).

### Agent Orchestration
- A coding agent working in one Spaces terminal can inspect the other coding agents on this device through `spaces agent list` and `spaces agent status`, so a human can drive several agents from a single terminal. The same views are available as MCP tools (`spaces_agent_list`, `spaces_agent_status`, `spaces_agent_annotate`); `spaces agent signal` stays CLI-only and is never exposed as an MCP tool, so an orchestrating agent can read status but cannot forge another agent's status.
- `spaces agent list` reports every coding-agent session on this device — optionally narrowed to one workspace with `--workspace` — and `spaces agent status` reports a single session, defaulting to the current terminal's `SPACES_TERMINAL_TRACKING_ID` and accepting an explicit `--session`. Both fail when no matching agent session exists. Each row carries the agent's status, its note, the owning project and workspace and branch, whether it has reported a lifecycle signal yet, and a clickable `spaces://terminal/<session-id>` deep link to its pane. `--json` (and the `spaces_agent_list`/`spaces_agent_status`/`spaces_agent_annotate` MCP tools) emit the same fields as machine-readable JSON, with the rendered deep link under an `open` key and, for a row read from a paired device, the resolved device id under `deviceID`.
- `spaces agent annotate <note>` sets an explicit, human-authored note on a coding-agent session (defaulting to the current terminal's session, or an explicit `--session`). Notes are explicit only: Spaces never derives a note from prompts or terminal output. An empty note clears the annotation. Notes are single-line plain text, trimmed and length-capped, and survive status changes — only another annotate call changes a note. Annotating a terminal that has no coding-agent session fails with a clear error rather than creating one.
- `spaces agent spawn --command <cmd>` starts a supported coding agent (claude, codex, or opencode) in a new Spaces terminal in the current directory's workspace (or an explicit `--workspace`), then blocks until the daemon's foreground process classification identifies the agent running in that terminal — detection, not a hook signal — before returning. The command must launch a supported coding agent (so readiness knows which foreground kind to await); anything else fails loudly. Hooks are not a spawn prerequisite: readiness is detection-based because a promptless Codex never emits a first signal, and hooks can also be held behind an interactive trust review. The spawned command runs inside an interactive login shell, so it resolves whatever the user's own Spaces terminal resolves. If the command ends before it is ever detected — an unresolvable binary, an immediate crash — spawn fails at that moment and reports the child's exit and the last lines it printed (which carry the shell's own `command not found`), rather than blaming detection for a command that never ran. Detection otherwise has a default 90-second budget (`--timeout <seconds>`); if the command keeps running but is never detected, spawn exits non-zero, names the command it was waiting for, points at `spaces terminal tail <session>`, and leaves the session running. Spawn delivers no prompt: it returns as soon as the agent is detected, and the orchestrator gives the agent work by sending input with `spaces terminal send text <session> <text> --submit` and confirming progress with `spaces terminal tail`/`spaces agent status`. `--submit` is the one intended way to submit a prompt: it sends the text as a paste and then a separate Enter keystroke, so every supported agent TUI (Claude Code, Codex, OpenCode) runs the line instead of leaving it as an unsubmitted paste in the composer — no per-provider flag or mode is needed, and once the agent's TUI is running (bracketed paste on) the prompt is submitted as fast as the terminal accepts it; only a submit that lands before the application enables bracketed paste pays a short spacing delay that keeps its Enter distinct. Prompt delivery is the orchestrator's job, not spawn's, because a spawn-internal send cannot see or answer the common first-run states — a trust/onboarding dialog, an auth-gated agent, or provider timing flakiness — that hold or swallow input, while the orchestrator driving the session can. The spawning terminal is auto-subscribed to the new agent once the agent has an orchestration row (rows appear on the first hook signal); a spawn whose agent has not signaled yet is simply not auto-subscribed. `--title` overrides the default title (the agent's name). Spawn reports the child terminal session id, which agent was detected, whether it was auto-subscribed, and a `spaces://terminal/<session-id>` deep link; `--json` (and the `spaces_agent_spawn` MCP tool) emit the same fields as machine-readable JSON, with the rendered deep link under an `open` key.
- `spaces agent kill <session>` terminates a child coding-agent session and its terminal, addressing the child by its terminal session id. `kill` only terminates coding agents: a signaled child (one with an agent row) is stopped after its subscribers are told it exited, a not-yet-signaled session qualifies only when it was launched as a coding agent, and a session id that names an ordinary shell or process terminal is refused with "no agent session" instead of destroying that terminal. `spaces agent subscribe <session>` and `spaces agent unsubscribe <session>` record or remove a watch edge from the current terminal (or an explicit `--subscriber`) onto a child agent session; subscribing to a terminal whose coding agent has not emitted its first hook signal yet — a terminal with no coding-agent session at all, or one whose agent Spaces has only detected running but never received a signal from — fails loudly and tells you to retry after the agent starts working. These are available as the `spaces_agent_kill`, `spaces_agent_subscribe`, and `spaces_agent_unsubscribe` MCP tools.
- Spaces offers no command that claims to interrupt or cancel a coding agent's turn. An orchestrator that wants to try steering a child sends the keystroke itself — `spaces terminal send bytes <session> 27` for ESC — because ESC means whatever the agent's TUI decides in its current state: with a nested panel open (usage, a running shell view, a picker) it dismisses that panel and the agent keeps working. Spaces cannot see which state a TUI is in, so it never reports a keystroke as a cancelled turn. Sending input is a keystroke and nothing more: it records no agent status transition. Agent status changes only when the agent itself reports one through `spaces agent signal` (or a lifecycle hook that calls it), so an agent that keeps working after a keystroke keeps reporting that it is working. Ending a child outright is `spaces agent kill`.
- `spaces agent spawn`, `list`, `status`, `annotate`, `kill`, `subscribe`, and `unsubscribe` accept `--device <name-or-id>` (and the MCP tools an optional `device` argument) to act on, or watch, a paired device instead of this machine; the deep links they render are qualified with `?device=<id>`. Remote `spawn` requires `--workspace` (a remote spawn cannot infer a workspace from the current directory), returns on detection the same way a local spawn does, and auto-subscribes the current terminal to the remote child once that child has an agent row on the device. Remote `kill` works whether or not the child has signaled: it stops a signaled child through the coding-agent stop path, and terminates a not-yet-signaled session directly when it was launched as a coding agent — the same shell/process refusal as a local kill; a session that no longer exists fails with a clear error.
- `spaces agent subscribe <session> --device <name>` records a **cross-device watch**: the current terminal receives the same blocked/done/exited notification lines for a coding agent running on a paired device that it gets for a local child. The watch is delivered by this machine's daemon, which watches the paired device on the subscriber's behalf, so `--device` names where the child lives, not where the command runs; the subscriber is always the local terminal. Subscribing requires the device reachable and the child to have an agent session on it (otherwise it fails loudly). `spaces agent unsubscribe <session> --device <name>` removes the watch and works even when the device is offline. A `--device` that names this machine is not a cross-device watch: it is normalized onto the local path and validated with the same-device cycle guard (self-edges and subscription cycles are rejected). Cross-device subscription **cycles cannot be detected** — a paired device does not expose its own watch graph — so avoiding an A-watches-B-watches-A loop across two machines is the operator's responsibility; the same-device cycle guard still applies to local watches.
- When a watched child goes blocked, done, or exits, Spaces injects a single multi-line block into the subscribing terminal so the orchestrator (human or agent) is told without polling: a sentence line `[spaces] <label> (<kind>) is <blocked|done|exited>` followed by two-space-indented `key: value` lines in the order `project`, `workspace`, `branch`, `session`, `note`, `link`, where the `branch` line is omitted when the workspace has no branch and the `note` line when the child has no note. `<kind>` is the child's coding agent (`claude`/`codex`/`opencode`), which Spaces remembers for the session from the moment it identifies the agent, so the `exited` block still names it after the agent's process is gone; a child whose agent was never identified reads as the anonymous `coding agent`. `workspace` is the workspace's full directory path (so the orchestrator can locate the worktree on disk), with `branch` carried on its own line (including slashes) so it is never duplicated into the workspace field; `session` is the child's terminal session, the same id `link` (a `spaces://terminal/<session-id>` deep link) targets. The `project`, `workspace`, `session`, and `link` lines are always present so an orchestrating agent can parse them as fields rather than the deep link's URL. The block is a neutral event notice, not an instruction: it states what happened and carries the child's deep link as a bare reference, leaving the human or orchestrating agent to decide from context whether and how to respond. The `[spaces]` first line never begins with a character an agent TUI treats as command syntax, and the indented continuation lines are likewise safe; for a cross-device watch the link is device-qualified (`?device=<id>`) so it resolves the child on the right device. Spaces submits the block for the orchestrator reliably: the terminal send path delivers the text as a paste and the carriage return as a separate keystroke at the session host, because an agent TUI (Claude Code, Codex, OpenCode) treats a single burst of text plus return as an unsubmitted paste that would sit in the composer unrun.
- Injection only happens while the subscriber is idle — its own agent is idle or done, or it is a plain terminal with no agent. If the subscriber is busy (spinning or waiting) the notification is held and delivered the moment it next goes idle, so a line never lands mid-task. A busy orchestrator does not have to wait for its own turn boundary to learn a child changed state: while it is busy, any held events are also attached to the result of its next Spaces MCP tool call (`spaces_*`) as a `pendingAgentEvents` list of the same rendered blocks. Each held event is delivered exactly once — by whichever path reaches it first, the tool-call attachment or the idle injection — so an event picked up on a tool result is not injected again, and vice versa. While a subscriber is busy, repeated transitions of the same child collapse to a single held line showing the child's latest state (a child that goes blocked then done delivers one "done" line). A held "is blocked" notice is withdrawn if the child resumes working before delivery — whether the child is local or on a watched device — so a subscriber never receives a blocked line for an agent that is no longer blocked; held "done" and "exited" notices are terminal facts and are still delivered. If injecting a subscriber becomes impossible because its terminal has ended, its held notifications and its watch edges are dropped.
- A child's exit is announced to each of its subscribers exactly once, however the exit came to light. Only Claude Code reports its own session end, so a Codex or opencode child that quits is noticed by Spaces watching the terminal rather than told by the agent — and Spaces watches for that in more than one way. Whichever notices first is the one that announces it: the subscriber receives one `is exited` block, and the child's lifecycle history records one exit, never a pair that would prompt an orchestrating agent to act twice on one exit. The same holds when the child is being torn down at that moment — killed, or its terminal or workspace stopped: the announcement is still made once, never lost to the teardown and never doubled by it. A watcher that is busy when the exit happens receives the block when it next goes idle, so nothing is dropped for being announced at an inconvenient time.
- A terminal cannot subscribe to a coding agent running in itself, and Spaces rejects any subscription that would form a cycle of watchers (A watching B while B watches A), so notifications can never chase each other around a loop.
- Every `spaces://terminal/<session-id>` deep link that appears in agent list output and notification lines is clickable. Clicking one focuses that session's terminal pane: in the Mac app the pane opens (or is brought forward) in place; from an in-terminal click it focuses directly with no round trip through the OS; on iPhone and iPad the app opens the session's terminal. A link may carry `?device=<id>` to name the paired device the session lives on; a device-qualified link opens that session's terminal in a remote-attached pane — the same pane a manual navigation to that session opens. A link naming a session that no longer exists says so, a link naming a device that isn't paired reports the device is unknown, and a link whose session can't be found on the named device says so. On the Mac, a pairing link (`spaces://pair`) opened here directs the user to pair from their phone instead of being silently dropped, and an unrecognized `spaces://` link is reported.

### Agent Hook Installation
- Spaces wires each supported coding agent's global hooks to `spaces agent signal` so agents report their state. Supported agents are Claude Code (`~/.claude/settings.json`), Codex (`~/.codex/hooks.json`, with `features.hooks = true` in `~/.codex/config.toml`), and opencode (a plugin file under `~/.config/opencode/plugin/`). The wired events cover session start, prompt submission, the start and the completion of each tool use (completion is what returns a blocked Claude Code or Codex agent to working after an approval), permission prompts, and turn completion; Claude Code additionally reports session end, which Codex and opencode do not expose, and opencode additionally reports the answer to a permission prompt, which Claude Code and Codex do not expose.
- Spaces never writes a coding agent's configuration without the user asking. Hooks are installed from the launch setup step or from Settings → Coding Agents, and from nowhere else.
- Generated hook commands invoke the Spaces CLI by the absolute path resolved on the agent's host at install time, in the form `'<path>/spaces' agent signal <event> >/dev/null 2>&1 || true # spaces-agent-hook v<N>`. Installed Linux daemons use the stable `~/.spaces/bin/spaces` path rather than a versioned release path, so daemon updates keep existing hooks on the active CLI. Other installations use the resolved executable path and require hook reinstallation if that binary moves. Hook commands do not depend on `spaces` resolving on the hook process's `PATH`, which an agent need not pass through; a hook that silently could not find the CLI would report as installed while never firing. Installing hooks fails when the Spaces CLI cannot be found on that host. The CLI reports only from Spaces-managed terminal sessions and exits successfully in any other terminal.
- The trailing `v<N>` is the hook version, which Spaces bumps whenever the hooks it writes change. Each agent therefore reports one of three states: hooks not installed, hooks out of date (Spaces-owned hooks are present, but an older Spaces wrote them, or this release binds a lifecycle event they do not cover), or hooks installed. Codex counts as out of date when its hook entries are current but `features.hooks` is not enabled, because the hooks exist and cannot fire.
- Installing over out-of-date hooks replaces them rather than adding beside them, so an agent never accumulates one Spaces hook per Spaces release.
- An agent is available only when its CLI executable resolves on the daemon host through the daemon PATH, common user executable directories, or the daemon user's login-shell PATH. Installation targets the home directory of the machine that agent runs on and is idempotent: it adds exactly one Spaces entry per lifecycle event and never duplicates an entry on repeat runs. A JSON hooks object or mapped event with an unsupported shape is left untouched and reported as an installation failure. The opencode plugin path is written only when it is absent or already carries the Spaces ownership marker; an unrelated file at that path is left untouched and reported as an installation failure.
- Installation preserves a config the user manages elsewhere: when an agent's config file is a symlink into a dotfiles repository, the hooks are written through to the linked file and the symlink is left in place.
- Codex feature enablement is delegated entirely to the Codex CLI, including any normalization it applies to `config.toml`. Spaces reports installation success only when a subsequent Codex CLI status command confirms that the hooks feature is effectively enabled.
- Agents install independently. One agent whose config cannot be edited, or whose CLI is not detected, does not prevent the others in the same request from installing.
- Settings includes a Coding Agents section listing supported agents for a selected device (This Mac or a paired remote), showing whether each agent CLI is detected and how completely its Spaces hooks are installed, with a status indicator and an Install, Update, or Reinstall action only for detected agents.
- An agent whose install just failed shows that failure's reason on its own row, until an install for that agent succeeds.
- The supported-agent rows remain visible while status loads or cannot be fetched; loading and error messages appear below the rows.

#### Coding-Agents Setup Step
- When a coding agent is detected on This Mac whose hooks are missing or out of date, launch offers a skippable coding-agents setup step after the Chrome Automation step. It shows the same agent rows as Settings, so hooks can be installed for This Mac or any paired device from the step itself.
- The step offers Skip and Continue. Both dismiss it, and Continue reads Done once every detected agent on This Mac carries current hooks.
- Dismissing the step is remembered against the hook version it was dismissed for. A user who skips is not asked again until a Spaces release changes the hooks it wants to write, at which point the step is offered once more. A dismissal covers that hook version, not the agents installed when it was made: installing another agent afterwards does not re-offer the step, and its hooks stay available from Settings.
- Only Skip and Continue dismiss the step. A launch that finds nothing to install — no coding agent detected on This Mac, or every detected agent already carrying current hooks — records nothing, so a user who installs a coding agent later is still offered the step on the next launch.
- The decision to show the step reads This Mac only, so launch never waits on a paired remote that is asleep or unreachable.
- When the local daemon cannot report agent status, the step is skipped for that launch and is not recorded as dismissed, so it is offered again once the daemon answers. Launch never blocks waiting for it.

## Errors and Feedback
- Long-running actions should show visible progress.
- A workspace or project operation's progress indicator should appear only while that workspace or project is the active selection, so it never covers or blocks actions on an unrelated workspace; navigating away hides it and returning while the operation is still in flight shows it again.
- Failure states should be explicit and actionable.
- The GUI should prefer inline guidance over silent failure or hidden background behavior.
- Remote-device setup should use user-facing status and error messages: Macs need the Spaces app installed, while supported Linux devices are set up automatically over SSH.
- Background sidebar/runtime refresh should update in place without replacing the current detail pane or resetting the selected workspace tab. An open dialog window — New Project, New Workspace, project settings — stays open across those refreshes whatever pane is behind it, including Alerts; only the user moving the detail pane to different content dismisses it.

## Update Experience
- The app should check for updates periodically and allow manual update checks.
- Spaces ships two update channels: stable, cut from a version tag, and nightly, cut from the tip of the main branch once a day. Each build carries its own Sparkle appcast feed, so a stable install only ever offers stable releases and a nightly install only ever offers nightly builds.
- The channel is a property of the installed build, not a setting. A Mac moves to the nightly channel by installing a nightly build and returns to stable by installing a stable release; there is one Spaces app, and the two channels are never installed side by side.
- A nightly build's version is the stable version it was built from plus the time it was built, such as `0.5.1.202607250900`, so it reads as newer than that release, older than the next one, and distinct from every other nightly. Every message that names a version — the daemon compatibility hints below, `spaces --version`, the app menu — reports it unchanged.
- Nightly builds are unannounced: they are not linked from the website or the docs, and the page that serves them asks search engines not to index it.
- Update discovery and installation should use each channel's Sparkle appcast feed. Manual downloads may still be published separately, but the in-app updater should not depend on GitHub release APIs.
- The manual-download DMG should present a single guided installer entry point that installs `Spaces.app`, links `/usr/local/bin/spaces`, `/usr/local/bin/spacesd`, and `/usr/local/bin/spaces-caddy` to the app bundle resources, creates `~/.spaces/bin/spaces` and `~/.spaces/bin/spacesd` helper links to the same resources, and writes the per-user LaunchAgent used by built-in terminal commands and remote Mac pairing.
- The Ubuntu 24.04 install/upgrade path should install release-managed daemon helpers under `~/.spaces`, expose `spaces` at `~/.local/bin/spaces` for normal terminal use, and run the user systemd service from `~/.spaces/bin/spacesd`.
- An Ubuntu upgrade with a running daemon should preserve that daemon's pid and sessions through the in-place update, including while long transcript replay keeps it temporarily unavailable. The installer should leave an active daemon untouched and report an error when the in-place handoff cannot be accepted or does not reach the installed image; systemd should start the service only when no daemon is running. Rapid repeated handoffs to the same version should be refused as an exec loop, while a daemon that remains stable for at least one minute after session replay finishes should accept a later same-version development build.
- When launched from `/Applications/Spaces.app`, the app should keep Spaces-owned helper links and the LaunchAgent plist aligned with the installed app bundle without restarting `spacesd` automatically.
- `spaces --version` should report the current version.

### Daemon Compatibility and Restart
- A client app and the daemon on a device can run different versions because they update on their own schedules. As long as they remain compatible, updating the app does not require restarting the daemon, and running terminals, processes, and coding agents keep going uninterrupted.
- A running daemon exclusively owns schema upgrades for its profile database. A staged CLI or test helper that needs a newer schema refuses to migrate beneath that daemon and directs the user to `spaces daemon apply-update`, which loads the staged daemon in place before the upgrade and preserves its sessions. If daemon startup overlaps a helper-owned migration, startup waits for the migration and then proceeds without requiring another request.
- When a device has a newer Spaces installed than the build its daemon is running, that device shows an "update pending" hint while the Mac app applies the staged update in place, on its own and without prompting: running terminals, processes, and coding agents are not interrupted, and the hint clears once the daemon comes back on the new build. Whether an update is waiting is a fact about that device, reported by that device, so every client says the same thing about it — a client's own version never enters into it.
- When a device's daemon is too old for the current app, that one device is blocked with an explanation while every other paired device stays usable. If instead the app is too old for the daemon, the block asks the user to update the app.
- An Update Daemon action appears only when a device reports a newer Spaces already installed than the build its daemon runs. A daemon restart re-execs whatever is installed on that device, so it applies a staged update and changes nothing otherwise; offering it in that second case would give the user a button that cannot resolve their warning. The action needs no impact warning or confirmation, because the in-place restart preserves running terminals, processes, and coding agents, and it is offered for every kind of device — including a remote Linux daemon whose newer release is installed but not yet running. If the request fails because the device is unreachable or rejects it, Spaces shows the error.
- When a device's daemon is too old and nothing newer is installed there, no update action is offered and the app instead says where to install one: for a remote Mac, to open Spaces on that Mac; for this Mac, a Check for Updates action that looks for an update directly; for a Linux device, the version-pinned install command to run there, which updates the daemon and resumes its sessions in place. Once a newer Spaces is installed on a Mac, its daemon picks the update up on its own.
- These messages name the versions involved — the build the daemon is running, the build installed on that device, and the app's own version — so it is clear which machine is behind. The versions are context for the user; what Spaces offers is decided from what the device reports about itself, never by comparing an app's version against a daemon's.
- A `spacesd` that has started shutting down — an explicit stop or restart (such as Restart Local Daemon), or an in-place update handoff — refuses every request until it exits or the replacement image is ready, not only requests that would start new work. A request that races the shutdown gets a clear "shutting down" response instead of running, partially running, or silently racing a daemon that is already tearing down, including a liveness `.ping` reporting the daemon not-live.
- A client that finds no live daemon tells these two teardown cases apart rather than treating both alike: during an in-place update handoff it waits briefly for the replacement image to finish starting, since one is already on its way; during a plain stop or restart it starts a fresh daemon immediately, since nothing else is coming. Either way the client ends up with a running daemon — the difference is only whether it waits for one already in flight or starts its own.
- The iPhone app can apply an update already staged on a device, including when nothing else would — the Mac app applies staged updates on its own, but only while it is running. After requesting the update, the action reports that it is updating for as long as it waits, and the app watches for the daemon to return and clears the warning itself. The device stays marked as needing attention throughout, since it is deliberately offline while its daemon restarts. If the daemon does not come back within about half a minute, the action becomes available again to retry and the warning simply remains rather than reporting a failure, since a slow restart and a refused one look the same from here.
